# AGENTS.md

Постоянный контекст каждой задачи: стиль, терминология, рабочие правила
и безопасность. Архитектуру, историю и инструкции отдельных процедур сюда не добавляй.

## Документация

- Пиши **кратко, лаконично и всеобъемлюще**: все существенные условия,
  ограничения и причины, без воды, повторов и ненужной истории. Одним словом, так, чтобы удобно было читать человеку.
- Документация — на русском; код, комментарии и commit messages — по
  существующим соглашениям проекта.
- Корневой `README.md` — описание проекта и технический вход для разработчика:
  установка, настройка, команды, проверки и навигация.
- [ADR](docs/adr/index.md): бизнес-решения и архитектурные подходы описывай
  **в том числе в текущем состоянии**, а не только при изменении.
  Для технического стека фиксируй только существенные изменения; исходный
  набор технологий описывается в README и профильной документации.
  Ровно одно решение на ADR: контекст, альтернативы, причины и последствия.
- Принятие ADR — владельцем проекта; имя `NNNN-kebab-case.md`, следующий
  номер после максимального (первый — `0001`). После публикации номера
  и смысл записей неизменны.
- Перед изменением прочитай реестр, относящиеся к задаче ADR и их последующие
  изменения. Пересмотр — новый ADR с причиной, ссылкой и точной областью замены;
  в старом обнови статус и обратную ссылку. Больший номер сам ничего не отменяет.
- [План](docs/plan.md) — требования и acceptance; [обзор](docs/architecture.md) —
  навигация по архитектуре. Обновляй затронутые документы вместе с решением,
  не дублируй обоснования из ADR. Противоречия сначала согласуй с владельцем.
- Принятое решение и готовый код не означают прохождения live acceptance
  или разрешения на operator-gated действия.

## Стиль и терминология

- Следуй стилю соседнего кода; используй существующие типы и утилиты,
  не вводи параллельные соглашения и абстракции без необходимости.
- Для длительных CLI-операций прогресс — хороший тон: переиспользуй общий
  renderer, показывай в TTY одну обновляемую строку со стадией, временем и
  счётчиком; progress bar — при известном объёме, spinner — при неизвестном.
  Не выдумывай проценты/ETA и не засоряй терминал строкой на каждый batch.
  Прогресс направляй в stderr, сохраняя машинный stdout чистым; без TTY —
  редкие сообщения без ANSI. При успехе, ошибке и отмене очищай строку и таймер.
- Идентификаторы — на английском; type-only импорты — `import type`,
  относительные TypeScript-импорты — с `.ts`. Комментарии объясняют причины,
  ограничения и неочевидные последствия, а не пересказывают код.
- Харнесс — приложение, ведущее диалог; вендор — производитель модели;
  provider — сервис, выполняющий API-запрос.
- Raw — исходные данные; canonical — нормализованный корпус;
  projection — производное представление. Не используй эти термины как синонимы.

## Работа и безопасность

- Версии parser/extractor и форматов сверяй с константами реализации,
  не копируй их номера в рабочие инструкции.
- Не меняй БД, не запускай миграции, paid API или recovery без разрешения
  пользователя и предусмотренных командой проверок/подтверждений.
- Перед операциями с архивом прочитай относящиеся к ним ADR и
  [recovery runbook](docs/rocksdb-recovery.md). Не обходи защитные проверки.
- `/Volumes/Archive/Legacy Conversations/` не изменяй и не удаляй.
  Физическое удаление исходного архива выполняет только пользователь.
- External System и проект `other-project` не изменяй.
- `.env`, secrets, приватные диалоги и полные raw-файлы не коммить;
  fixtures должны быть обезличены.
- Git-мутации (commit/push/reset/rebase) — только по явному запросу пользователя.
- Проверяй затронутое поведение; сообщай, что выполнено, что пропущено
  и какие operator gates остаются открытыми.
