# ai-baka

**Локальный архив и поиск по диалогам с AI-агентами.** ai-baka собирает историю
из разных приложений, сохраняет исходные файлы и приводит сообщения к общей
модели. Помогает найти старое решение, сохранить диалоги после удаления
исходников и работать с историей независимо от интерфейса конкретного агента.

Это CLI на Bun/TypeScript с SurrealDB. Архивация и полнотекстовый поиск работают
локально, без API-ключей; векторный поиск — отдельная опциональная возможность.

Текущая версия — **0.1.0**. Реализованные возможности и ограничения выпуска
описаны в [истории изменений](CHANGELOG.md).

## Поддерживаемые харнессы и вендоры

Харнесс — приложение, в котором ведётся диалог; вендор — производитель модели.
Один харнесс может использовать модели разных вендоров.

| Харнесс | Идентификатор для CLI | Источники |
| --- | --- | --- |
| OpenAI Codex | `codex` | Rollout JSONL, включая сессии Codex в Orca |
| Claude Code | `claude-code` | JSONL проектов и истории |
| Claude Desktop | `claude-desktop` | Локальные сессии JSON/JSONL, LevelDB fallback |
| OpenCode | `opencode` | SQLite |
| Cursor | `cursor` | SQLite workspace/global storage и связанные файлы |
| Qwen Code | `qwen-code` | JSONL проектов |
| Kimi Code / Kimi CLI | `kimi-code` | Каталоги сессий, JSONL и JSON-метаданные |
| Oh My Pi (OMP) | `omp` | JSONL сессий, включая дочерних агентов |

Распознаются вендоры **OpenAI, Anthropic, Alibaba, Google, Meta и Moonshot AI**.
Неопределённый вендор сохраняется как `unknown`. Это нормализация метаданных
архива, а не прямые API-интеграции со всеми перечисленными компаниями.
Реальный провайдер эмбеддингов сейчас — **OpenAI**; mock используется в тестах.

Поддержка зависит от локального формата: не каждый служебный файл содержит
диалог. Такие файлы могут сохраняться в raw-архиве без попадания в поиск.
Пути и особенности парсеров — в [источниках данных](docs/sources.md).

## Установка

Проект устанавливается **из исходников**; `package.json` помечен `private`.
Основной проверенный сценарий — macOS. В коде есть поддержка хранения на Linux,
но это не означает полной проверки всех харнессов и операций на каждой ОС.
Нативный Windows не поддерживается проверкой хранилища; для него используйте
WSL2 как экспериментальный Linux-сценарий.

### Зависимости по платформам

Нужны Git, [Bun](https://bun.sh/docs/installation) (рекомендуется 1.3 или новее)
и Docker с Compose v2. Node.js не заменяет Bun: проект использует `bun:sqlite`.
SurrealDB 3.2.4 загружается через Compose; версия и digest образа закреплены
в репозитории.

Для существующего архива смена образа — отдельное обслуживание: сначала backup,
проверка restore и совместимости на тестовой БД, затем обновление production.
Обновление исходников не обновляет запущенный контейнер автоматически.
Restore evidence от прежнего pinned образа потребует новой проверки; после
обновления tiktoken также пересоздайте exact-token отчёты и зависящие от них планы.

| Платформа | Подготовка |
| --- | --- |
| **macOS** | Установите Git (`xcode-select --install`), Bun по официальной инструкции и [Docker Desktop](https://docs.docker.com/desktop/setup/install/mac-install/). Запустите Docker Desktop. Live DB должна лежать на внутреннем APFS. |
| **Linux** | Установите Git средствами дистрибутива, Bun и [Docker Engine с Compose plugin](https://docs.docker.com/engine/install/). Запустите Docker и настройте доступ к нему для текущего пользователя. Для live DB допускаются ext2/3/4, XFS и Btrfs. |
| **Windows / WSL2** | Установите [WSL2](https://learn.microsoft.com/windows/wsl/install) и [Docker Desktop с WSL integration](https://docs.docker.com/desktop/features/wsl/). Git и Bun установите внутри Linux-дистрибутива. Все команды ниже выполняйте там; репозиторий и live DB храните в Linux FS, не в `/mnt/c`. |

Для backup/restore нужны `curl` и средства сжатия: `zstd` либо `gzip`.
Точный подсчёт токенов дополнительно использует [uv](https://docs.astral.sh/uv/getting-started/installation/).
Для обычного sync и текстового поиска uv не нужен.

Проверьте окружение:

```sh
bun --version
docker compose version
docker info
```

### 1. Получите исходники

Склонируйте этот репозиторий по URL из кнопки **Code**, затем в его каталоге:

```sh
bun install --frozen-lockfile
cp .env.example .env
```

Далее все команды выполняются из корня репозитория: Bun читает `.env`,
а обёртка Compose использует файл `.env` из этого каталога.

### 2. Настройте хранилище

В `.env` задайте **свои абсолютные пути** и пароль SurrealDB. Личные пути
из `.env.example` не нужно воспроизводить.

| Переменная | Назначение |
| --- | --- |
| `BAKA_ARCHIVE_ROOT` | Raw-снимки, manifests, exports и backups на смонтированном томе |
| `BAKA_DB_ROOT` | Отдельный каталог live RocksDB на внутреннем диске; не внутри архива |
| `SURREAL_USER`, `SURREAL_PASS` | Учётные данные БД; замените пример `root/root` |
| `SURREAL_URL` | Оставьте `ws://127.0.0.1:8901/rpc` для стандартного Compose |
| `SURREAL_NAMESPACE`, `SURREAL_DATABASE` | Оставьте `baka` и `archive` для новой установки |

Примеры путей — замените имя пользователя и точку монтирования:

| Платформа | `BAKA_ARCHIVE_ROOT` | `BAKA_DB_ROOT` |
| --- | --- | --- |
| macOS | `/Volumes/Archive/ai-baka` | `/Users/alice/Library/Application Support/ai-baka/rocksdb` |
| Linux | `/mnt/archive/ai-baka` | `/home/alice/.local/share/ai-baka/rocksdb` |
| WSL2 | `/mnt/archive/ai-baka` на отдельно подключённом томе | `/home/alice/.local/share/ai-baka/rocksdb` внутри WSL |

**Ограничение текущего preflight:** архив должен находиться на файловой системе
с другим device ID, чем `/`. Обычная папка на корневой FS Linux/WSL не подойдёт;
само создание `/mnt/archive` не монтирует том. Подключите хранилище **до**
инициализации. Проверка записи требует минимум 1 GiB свободного места по
умолчанию; размер самой БД и резерв для индексов рассчитываются отдельно.

Live RocksDB не поддерживает ExFAT. Корни БД и архива должны быть раздельными;
для live DB не используйте пути через симлинки. На Linux/WSL явно задайте
`BAKA_DB_ROOT`: его default сейчас имеет macOS-структуру пути.

### 3. Проверьте источники и запустите архив

```sh
bun run baka discover
```

Корни по умолчанию ориентированы на macOS. Если источники не найдены, задайте
их в `.env`, особенно для Cursor/Claude Desktop на Linux и Windows:

```dotenv
BAKA_SOURCES__CODEX=~/.codex/sessions,~/.codex/archived_sessions
BAKA_SOURCES__OMP=~/.omp/agent/sessions
```

Значение — список путей через запятую; `~` разворачивается в home. Override
**заменяет**, а не дополняет стандартные корни этого харнесса. В WSL пути
к Windows-источникам должны быть доступны из Linux. Полный список переменных —
в [.env.example](.env.example), стандартные пути — в [docs/sources.md](docs/sources.md).

Для **нового** архива:

```sh
bun run baka archive:init       # один раз: каталоги и файл идентичности архива
bun run baka db preflight       # проверка тома, прав и свободного места
bun run baka db up              # запуск локального SurrealDB
bun run baka db migrate         # применение схемы
bun run baka sync --dry-run     # предварительная проверка без записи
bun run baka sync
bun run baka search "authentication"
bun run baka status
```

Для ежедневного запуска достаточно `bun sync`. Команда проверяет архив,
берёт process lock и проверяет готовность БД. Если локальная БД
(`127.0.0.1:8901` или `localhost:8901`) недоступна, после проверки безопасности
`BAKA_DB_ROOT` проверяет Docker API. На macOS недоступный OrbStack или Docker
Desktop запускается автоматически по выбранному Docker endpoint: одна попытка
запуска приложения, затем проверка API каждую секунду в течение максимум 60 секунд.
Каждая проверка ограничена одной секундой; при готовности sync продолжится сразу,
не дожидаясь конца минуты. По таймауту команда попросит включить Docker вручную
и повторить `bun sync`. Если CLI или приложение отсутствует, сообщение содержит
ссылки на установку OrbStack / Docker Desktop и шаги первоначальной настройки.
Docker context не переключается; `DOCKER_CONTEXT` имеет приоритет над
`DOCKER_HOST`. Неизвестные и удалённые endpoints, а также daemon на Linux/WSL
нужно запускать вручную. Docker CLI и соответствующее приложение должны быть установлены.
Затем команда один раз запускает Docker Compose: readiness wait — 45 секунд,
общий предел Compose — 60 секунд, отдельно от ожидания Docker API.
Уже доступная БД не перезапускается; другой endpoint автоматически не поднимается.
Проверка HTTP ограничена 2 секундами, подключение SDK с авторизацией — 10 секундами;
для sync автоматические переподключения SDK отключены. При ошибке команда
освобождает lock и завершается с ненулевым кодом, без цикла повторных запусков.
Это относится и к `bun sync --dry-run`: БД может быть запущена, но записи
в БД и raw не выполняются. Инициализация схемы остаётся отдельным `db migrate`.

В интерактивном терминале замечания при обработке файлов учитываются в строке
прогресса без отдельных сообщений на каждый файл. При завершении выводится
одна сводка по причинам (например, неподдерживаемый формат или частичная
обработка). Счётчик замечаний считает события, а не отдельные ошибки внутри
файла; итоговый `ingestErrors` сохраняет полный счётчик ошибок синхронизации.
`bun sync --json` оставляет подробный JSONL-журнал событий в stderr и итоговую
JSON-сводку в stdout.

`archive:init` откажет, если архив уже инициализирован. Для остановки БД:
`bun run baka db down`. Порт `8901` и имя контейнера `baka-surrealdb` должны
быть свободны. Команда `disk eject` использует macOS `diskutil`; на Linux/WSL
останавливайте БД и размонтируйте диск средствами ОС.

## Обновление

Инструкция ниже — для перехода с опубликованного релиза на следующий
поддерживаемый релиз. В **0.1.0** версия схемы — **1**, весь её состав находится
в `schema/0001_initial.surql`. Новые миграции появляются только для следующих
релизов; повторный `db migrate` на актуальной схеме ничего не применяет.
Версия приложения (`--version`) и номер схемы (`db status`) различаются.

### 1. Подготовьте окно обслуживания и резервную копию

Прочитайте [CHANGELOG.md](CHANGELOG.md) целевого релиза. Завершите sync,
reparse, migration, embedding workers и отключите их автоматические запуски;
не запускайте другие операции записи до окончания обновления. Сохраните
локальные изменения исходников отдельно; `.env` и приватные данные в Git
не добавляйте.

Следующие команды выполняйте **старой версией**, пока её БД ещё работает:

```sh
bun run baka --version
bun run baka db status
bun run baka validate
bun run baka backup --json
```

Сохраните `exportPath` и `manifestPath` из результата backup. Проверьте
**именно эту** копию; замените пример ниже полученным абсолютным путём:

```sh
BACKUP_EXPORT="/absolute/path/to/backup.surql.zst" # либо .surql.gz
bun run baka restore:test "$BACKUP_EXPORT" --json
bun run baka raw:verify
bun run baka db down
```

`restore:test` временно останавливает основную БД, использует отдельный
контейнер и затем запускает основную БД обратно. Ему нужны ресурсы,
указанные в разделе о восстановлении. Любая ошибка backup, restore или
validate — причина остановить обновление. Сохраните проверенные artifacts
и raw; для защиты от потери диска нужна копия на другом физическом устройстве
(workflow `backup off-device plan|run|verify`).

### 2. Обновите исходники и зависимости

В каталоге репозитория выберите **реально опубликованный тег** нужного релиза
на GitHub; `vX.Y.Z` ниже — обозначение для замены, не существующий тег:

```sh
TARGET_TAG="vX.Y.Z"
git fetch --tags origin
git switch --detach "$TARGET_TAG"
bun install --frozen-lockfile
bun run baka --version
```

Не перезаписывайте `.env` файлом `.env.example`: сравните их и добавьте только
новые обязательные параметры. Сохраните прежние `BAKA_ARCHIVE_ROOT`,
`BAKA_DB_ROOT`, namespace/database и credentials. Смена пути к БД не является
обновлением и может привести к запуску пустого хранилища.

Если релиз меняет image SurrealDB, **до запуска production** выполните
предписанную этим релизом проверку совместимости и restore на отдельной
тестовой БД с новым exact pin. Проверка старым образом не заменяет эту
проверку. Не открывайте ценный RocksDB новым образом наугад.

### 3. Примените миграции и проверьте результат

После выполнения дополнительных требований целевого релиза:

```sh
bun run baka db preflight
bun run baka db up
bun run baka db migrate
bun run baka db status
bun run baka validate
bun run baka status
bun run baka search "известная фраза из вашего архива"
```

`db up` запускает БД с Compose-конфигурацией выбранного релиза;
`db migrate` проверяет checksums и применяет только новые миграции.
Не редактируйте уже применённые `.surql` и записи `schema_migration`.
Возобновляйте автоматический sync и workers только после успешной проверки.

Если changelog требует пересоздать производные данные, выполните указанные
там команды. Например, после изменений парсеров:

```sh
bun run baka reparse --only-outdated --dry-run --harness codex
bun run baka reparse --only-outdated --harness codex
```

Выберите затронутый харнесс. Для изменения search projection используется
`bun run baka search:rebuild`. Это не обязательные шаги каждого обновления.
Изменения tokenizer или embedding pipeline требуют новых exact-token
отчётов и связанных планов; платный backfill не запускается автоматически.

### Если обновление не прошло

Остановите writers и сохраните ошибку, проверенный backup и текущую БД.
Не выполняйте `db migrate` повторно вслепую после частичного сбоя.
Переключение Git на старый тег **не откатывает** схему или формат RocksDB;
обратные миграции автоматически не выполняются. Восстановление делается
по [runbook](docs/rocksdb-recovery.md) в отдельное свежее хранилище с
совместимой версией приложения/SurrealDB, без удаления исходной БД.

### Дорелизная БД с цепочкой 0001–0009

Свёртка в начальную схему 0.1.0 — **не миграция существующей БД**. Старая
цепочка и checksum прежнего `0001_initial.surql` несовместимы с новым файлом.
Обычная последовательность обновления выше для неё не подходит.
Сначала сохраните backup и проверьте restore **исходной дорелизной версией**.
Не удаляйте журнал миграций и не подменяйте номера/checksum, в том числе
в manifests. Автоматического переноса этой БД в baseline 1 в CLI нет;
он требует отдельной согласованной процедуры с проверкой сохранности данных.
Новый релиз также не принимает старые schema 4–9 backup artifacts за schema 1.

## Возможности

### Синхронизация без потери исходников

- Автоматическое обнаружение источников и инкрементальная обработка изменений.
- Неизменяемые raw-снимки с SHA-256; SQLite снимается с учётом WAL, не простым копированием файла.
- История ревизий: удаление исходника не удаляет архив; неполный scan не подтверждает удаление.
- Общая модель диалогов, сообщений, tool calls/results, reasoning и usage, если они есть в источнике.
- Происхождение данных: машина, OS-аккаунт, харнесс, workspace, модель и reasoning effort.
- Повторный разбор сохранённых raw после обновления парсера без обращения к живому источнику.

```sh
bun run baka sync --harness codex
bun run baka reparse --harness codex --only-outdated --dry-run
```

Sync не вызывает OpenAI. При активном embedding space он может поставить
задания в очередь; `--no-enqueue-embeddings` отключает и это.

### Поиск и экспорт

Текстовый поиск использует BM25 по реальным пользовательским сообщениям и
финальным видимым ответам ассистента **текущих ревизий**. Есть фильтры по
харнессу, машине, пользователю, workspace, вендору, модели, роли и датам.

```sh
bun run baka search "sqlite backup" --harness codex --limit 10
bun run baka search "migration" --vendor anthropic --from 2026-01-01 --json
bun run baka export-thread <dialogue-id> --output dialogue.json
```

Экспорт диалога — canonical JSON; пути к исходникам исключены по умолчанию.
Сам текст диалога **не анонимизируется**.

Исторические ревизии, reasoning и tool-содержимое сохраняются в корпусе,
но не входят в обычный поисковый индекс. Старые флаги `--all-revisions`,
`--include-reasoning`, `--include-tools`, `--include-system` отвергаются,
а не включают скрытое сканирование всего архива.

### Векторный и гибридный поиск

Векторный поиск использует HNSW, гибридный объединяет его с BM25 через RRF,
убирает дубли сообщений и ограничивает число результатов из одного диалога.
Без готового active embedding space или API-ключа vector недоступен,
а hybrid переходит в текстовый режим с предупреждением.

Эмбеддинги требуют отдельной настройки и могут стоить денег:

1. Настройте `OPENAI_API_KEY`, исключения `EMBEDDINGS_EXCLUDE_*` и лимит размера документов.
2. Оцените объём через `embeddings plan`; для точного подсчёта есть `embeddings exact-tokens`.
3. Создайте candidate spaces, сравните качество через `embeddings candidates` и `relevance`.
4. Выполните подтверждённый `embeddings backfill` и финальную full-corpus проверку качества.

Это не однокомандный quickstart: платные операции требуют планов и явных
подтверждений. Общая команда `embeddings run` намеренно отказывает; используйте
`embeddings candidates run` и `embeddings backfill run`. Оценка цены берётся
из `OPENAI_EMBEDDING_PRICE_PER_1M_TOKENS`, не из встроенного тарифа.
Подробности — [план, §13 и §21](docs/plan.md) и `--help` соответствующей команды.

### Проверка, резервные копии и восстановление

| Команда после `bun run baka` | Что делает |
| --- | --- |
| `status` | Сводка sync, backup, restore и миграции |
| `validate` | Проверка связей, ревизий, raw и поисковых/векторных данных |
| `raw:verify` | Сверка наличия, размеров и SHA-256 raw-файлов |
| `doctor` | Диагностика; исправления только с явными флагами и `--apply` |
| `backup` | Logical export БД, сжатие и manifest с контрольными суммами |
| `backup off-device plan\|run\|verify` | Планирование, копирование и проверка bundle на другом устройстве |
| `restore:test` | Проверка восстановления в отдельном временном контейнере |
| `search:rebuild` | Перестроение поискового индекса из canonical corpus |

**`restore:test` временно останавливает основную БД.** Это операция обслуживания,
не безобидная проверка подключения; нужны Docker, свободный диск и ресурсы
для отдельного контейнера с профилем 12 GiB RAM / 4 CPU. Сверка checksum
доказывает целостность backup, но не заменяет проверку его происхождения.
Копия на том же физическом диске не защищает от потери этого диска.

Аварийное восстановление RocksDB описано в отдельном
[runbook](docs/rocksdb-recovery.md). Не подменяйте его копированием файлов живой БД.

### Миграция старого архива

`migration plan|run|retry|status` предназначены для SQLite-архива прежнего
проекта baka, **не для произвольных SQLite-файлов**. Исходный архив остаётся
read-only; выполняется построчная сверка, проблемные записи уходят в quarantine.
Запись требует подписанных разрешений и проверенных backup/restore artifacts.
Новым пользователям этот workflow не нужен. Требования — [план, §15](docs/plan.md).

## Приватность и ограничения

- Raw, БД, exports и отчёты могут содержать приватный код, пути, промпты и секреты. Ограничьте доступ и используйте шифрование диска.
- Не публикуйте `.env`, API-ключи, реальные диалоги и полные raw-файлы. Для issues и тестов нужны обезличенные примеры.
- Локальные sync и BM25 не отправляют диалоги провайдерам. При генерации эмбеддингов контент выбранных документов отправляется OpenAI; векторные запросы также используют API.
- Compose публикует БД только на `127.0.0.1:8901`. Не открывайте её в сеть без отдельного проектирования доступа.
- Это локальный single-user CLI, не web-приложение, облачная служба, чат поверх архива или синхронизация между компьютерами.
- Проект активно развивается. Готовый код миграции, платного backfill и off-device backup не означает, что эти процедуры уже проверены на вашем архиве.

## Участие в разработке

Для начала полезны исправления парсеров, обезличенные fixtures, проверка
Linux/WSL и улучшение документации. Крупное изменение сначала обсудите в issue:
опишите задачу, ожидаемое поведение и совместимость с существующими архивами.

### Проверки

```sh
bun install --frozen-lockfile
bun run typecheck
bun run test
```

Интеграционные тесты без доступной SurrealDB явно пропускаются. Для их запуска
используйте **отдельную тестовую** SurrealDB той же закреплённой версии и
задайте `SURREAL_URL`, `SURREAL_USER`, `SURREAL_PASS`. Не направляйте тесты на
ценный архив: даже изолированные тестовые namespace используют ресурсы сервера.

В pull request укажите, что изменено и как проверено. Для исправления парсера
добавьте минимальный обезличенный пример, воспроизводящий ошибку. Не включайте
данные своей рабочей установки; документацию пишем на русском, код и
комментарии — по существующим соглашениям проекта.

### Навигация по коду

| Каталог | Назначение |
| --- | --- |
| `src/sources/`, `src/sync/` | Discovery, снимки источников и синхронизация |
| `src/parsers/` | Парсеры харнессов и нормализация |
| `src/db/`, `schema/` | Репозитории SurrealDB и миграции схемы |
| `src/search/`, `src/embeddings/` | Поисковые документы, BM25, векторы и очереди |
| `src/backup/`, `src/migration/` | Backup/restore и перенос legacy-архива |
| `src/cli.ts`, `tests/` | CLI и тесты |

Основные инварианты: raw неизменяемы; миграции схемы явные; удаление источника
не удаляет историю; поисковый индекс производен от корпуса; embeddings не
блокируют sync. Изменения форматов сверяйте с [планом](docs/plan.md).
